# QBankKit

The app's connection to the QBank server, with no UI: the API client, the session store, and the offline core. The app target and its screens build on it.

## What is in it

- **`QBankClient`** - the endpoints the app's screens use: sign-up for an email the owner added (`signUp`), password sign-in, session check, sign-out, signing out of every device at once (`signOutEverywhere`), which forgets the session here only once the server has ended them all, and password change; deleting the signed-in user account for good with its password (`deleteAccount`), which forgets the session here; semesters, courses with their pages, folders, sets and exams, terms, practice sets with her sitting (`PracticeSet.sitting`, the question she left off at) and her standing in the set (`SetRun`: new, midway, restarted or done, as the server sends it), ending that sitting (`startPracticeSetOver`), and restoring a replaced set; adding, renaming and removing a course's pages ("Exam 1" and the folders on it) and setting or clearing a page's badge (`PageBadge`: Exam, Concept or Study); making and renaming folders, putting a folder on a page, saving her folder order, and moving sets between folders; adding, renaming, moving, and archiving semesters and courses from Settings; answers (`recordAttempt`, keyed by `clientAttemptID`, and marked `fromReview` from the Review runner); Review and its runner; exam setup with per-folder wrong counts, start (`pool` `.all` or `.wrong`), read, and finish, with an exam's standing read from `status` (`ExamStatus`: running, grace or ended, as the server sends it) and not from `finishedAt` being nil; study place, the account's color scheme (`setPalette`, Dusk or Slate, on `Account.palette`), progress export, and the whole bank as bank archive v1 for Settings > Export my bank (`downloadBank`, `GET /api/me/bank`); Connect an agent for Settings: the agent waiting under the code she types (`agentPairing(code:)`), her answer (`approveAgentPairing`, `denyAgentPairing`), her agent keys (`agentKeys`), and revoking one (`revokeAgentKey`), never a key itself, with a set's `importedByAgent` naming the key that imported it; checking and importing a question file (`checkImport`, `importSet`, with its replace question); making questions on the accounts the server allows (`questionMakerStatus`, `questionJobs`, `startQuestionJob`, the samples and copies she checks, the result, and cancel); exam twins of the folders and pool she ticks on Exam setup (`twinJobs`, `startTwinJob`, `twinJob`, `cancelTwinJob`, and `startExam(courseID:on:)`, which sends a finished job's exam as the server wrote it); and deleting a course or study topic with everything in it, a set, a folder with every set in it, or a past exam, each in three steps: its preview (`courseDeletion`, `practiceSetDeletion`, `folderDeletion`, `examDeletion`) with the warning in the server's words and a `confirm`, the delete that sends that `confirm` (`deleteCourse`, `deletePracticeSet`, `deleteFolder`, `deleteExam`), and Undo for 30 days (`undoDeleteCourse`, `undoDeletePracticeSet`, `undoDeleteFolder`, `undoDeleteExam`), with `recentlyDeletedCourses` and a course's `recentlyDeleted` listing what Undo can still bring back. Calls are `async throws(QBankError)`. Sign-in stores the bearer token through a `SessionStore`, and every later call sends it as `Authorization: Bearer`. The client keeps no cookies. The only server fact here is the public address in `APIConfiguration.production`; there is no API key.
- **`SessionStore`** - `KeychainSessionStore` keeps the token, its expiry, and the account as one Keychain item under `<bundle id>.session` (this device only, readable after first unlock). `InMemorySessionStore` is for tests and previews.
- **`AttemptQueue`** - every answer is saved on the phone first, then sent oldest first. An answer made without signal waits and goes out when the connection is back. The server saves each `clientAttemptID` once and answers a repeat with the saved attempt, so a send whose reply was lost is simply sent again. An answer the server refuses (a 4xx such as `exam_finished`) leaves the queue and is reported; one that can succeed later (no signal, 5xx, 429, signed out, a temporary password) waits. `FilePendingAttemptStore` keeps the queue in `Application Support/QBankKit`.
- **`ContentCache`** - loaded semesters, courses, practice sets, terms, and Review lists, keyed by `CacheKey` and stamped with when they were saved. `FileContentCache` keeps one JSON file per value in `Application Support/QBankKit/Content`, out of backups.
- **`WaitingProgress`** - answers still waiting on the phone, counted into a set's and a course's answered and fully right counts, so a set practiced without signal shows her answers before they are sent. It never counts high: where the phone cannot know whether a question was answered before, it counts at least the waiting answers. They count in a set's sitting too, on its row and in `PracticeSet.counting(waiting:)`, so a night without signal opens at the right question, and they move the set's `SetRun` with them (a set whose questions are all answered is done, never midway).
- **`LocalStore`** - the phone's question bank: one SQLite file through the system library, or a private in-memory database for tests. It holds the twelve tables of `docs/on-phone-bank.md` under numbered schema steps written in Swift (`Store/Schema`), applied in order at open, each in one transaction, so a file made by any earlier step is brought up to date. `transaction` makes all of a body's changes or none, `savepoint` undoes part of one, and `read` refuses writes. The file lives in `Banks/<key>/`, kept in the device backup and under data protection. Only a free account's model uses it (`QBankClient.routingBank(to:)`), and only through a Debug launch scenario until sign-in arrives.
- **`LocalBank`** - the bank on the phone: an `HTTPTransport` over a `LocalStore` that answers the server's contract with the server's paths, JSON, status codes and refusal sentences, so a `QBankClient` talks to it as it talks to the server. Each rule family registers its routes into one router; it serves semesters, courses, topics, pages and folders, and the sets: the import check (the server's `checkImport`, ported), import, replacing a set or adding one beside it, restoring an earlier version, reading a set and a course's terms; and the study routes: recording an answer once for each id with progress that is never lowered, a set's sittings, run and Start over, a course's Review list, practice from it and clearing it, a course's counts and the course used last; exams: the plan (`ExamPlanner`, the server's `planExam`), the all and wrong pools over a folder's exam bank or its practice questions, start and replace, running, grace and time up told from the clock, finish, the result by folder and past exams; and deleting a set, folder, page, course or topic with its preview, confirmation and Undo for 30 days, a past exam too, with Recently deleted; and filing a sample set into a bank that has never held anything (`fileSampleSet`), through its own import into a topic made for it. It takes its clock, id generator and random draw from the caller, so tests set all three. `docs/on-phone-bank.md` is its design record. A free account's model uses it through `BankRoutedTransport`, which sends the bank's paths to it and every other path to the network, and `AccountKind` says which kind of account has its bank on the phone and what each kind can do; only a Debug launch scenario reaches a free account until sign-in arrives.
- **`BankArchive`** - the whole bank as bank archive v1, the document `docs/on-phone-bank.md` defines and the server's `/api/me/bank` speaks. `write(from:at:)` reads the twelve tables in one snapshot and writes the header, then each table in the format's order with its rows by key, a json field as its stored text. `read(_:into:)` stores a document into a bank that holds no row, whole or not at all: the file is scanned as strict JSON, every rule of the format is checked before the store is opened for writing (the format and version, every key, the counts against the lists, each field's kind, unique keys, a closed set of references, delete marks, the course and semester rule, and the server's own name rules for topics and folders), and the write runs in one transaction that counts what it stored against the document's counts and rolls back on any difference. A cut-off or altered file loads nothing, and a bank that already holds a row is never written into. `counts(of:)` gives the counts a sender compares with the answer to an upload. The phone does not run the import check on a document: a bank that came back from Cloud must load even if a rule has tightened since. Settings > Export my bank writes it for a free account.
- **`Scoring`** - the server's scoring rules and its feedback wording (Correct, Partly correct, the points line and the scoring rule), so an answer waiting to be sent shows the same mark the server records later; once saved, the app shows the server's own words (`SavedAttempt.pointsText` and `ruleText`, `ExamResult.Item.label`). The contract tests check it against the server's own marks for every format.
- **Models** - `Codable` types matching the server's responses. A question's format-specific `body` is read into `QuestionBody`, and kept as sent in `rawBody`, so tables, images, and fields added later survive the offline cache. A question format this version does not know decodes as `.unsupported` instead of failing the whole set. A course row carries a `kind`, `.course` or `.topic` (a study topic: no semester, an empty code), open so a kind added later still decodes; `CourseDetail.semester` is nil for a topic, and anything from before topics reads as a course.

## Tests

```sh
swift test --package-path Packages/QBankKit
```

`test/package-tests.sh` runs this on macOS in `xcode.yml`. On the iOS Simulator:

```sh
cd Packages/QBankKit
../../test/sim.sh -- xcodebuild test -scheme QBankKit \
  -destination 'platform=iOS Simulator,id={{UDID}}'
```

Nothing in a test run reaches the network: the client talks through `HTTPTransport`, and tests answer with recorded responses. The Keychain tests write real items under a throwaway service on macOS; a package test bundle on the iOS Simulator has no Keychain entitlement, so they skip there, and they skip wherever the login keychain is locked (a CI runner service with its own security session).

### Contract fixtures

`Tests/QBankKitTests/Fixtures/contract/` holds one exchange per file: the request the app sends and the response the server gave. Every file is a live recording from the server commit in `Fixtures/pin.json` and carries that commit as `recordedFrom`; a test requires it of every file. They hold no real student data and no real credentials.

`test/record-contract.sh` records them from a checkout of the pinned server. It copies the checkout to a scratch tree, adds the scenarios in `test/record-contract/`, and runs them there in-process: the server's own app over a throwaway in-memory database, with invented accounts and invented course content, and nothing over the network. Make questions and exam twins run on the server's own fake model (`apps/api/src/question-maker/fake-model.ts`), so no model is called. The end of the 30-day Undo window is reached the way the server's own tests reach it: the deleted row's `deleted_at` is moved 31 days back. The recorder fails when a scenario's call answers a status it did not expect, or when a fixture in the directory has no scenario.

A recording keeps what the server sent, rewritten only so that a re-record changes what the server changed and nothing else:

- Every id the server made becomes a fixed synthetic one: the id a test names where it names one, numbered in the order the server first sent it otherwise.
- Session tokens and agent keys become `synthetic-*` placeholders, user ids become `synthetic-user-N`, and agent pairing codes become fixed stand-ins.
- Times and delete `confirm` tokens stay as the server sent them, so tests read them from the recording instead of naming them.

`Tests/QBankKitTests/Fixtures/openapi.json` is a copy of the server's OpenAPI document (`apps/api/openapi.json` in the server repository, served at `https://qbank.dimitrygallego.com/openapi.json`). `Fixtures/pin.json` names the server commit that copy and every fixture come from. A test checks that every recorded call and status is documented there, that every key in a recorded response is allowed by that schema, and that every key the kit reads while decoding a recording (watched through a recording `Decoder`) is a property of it.

### Transcripts and the replay helper

`Tests/QBankKitTests/Fixtures/transcripts/` holds one file per scenario world: every call the scenario made to its throwaway server, in order, named or not, as the same request and answer a fixture keeps (with the same rewrites), plus each write the scenario made straight to the database to let time pass (the Undo window's end, an exam's time running out) as a `write` step naming the table, the row's id, the column and the time it then held. Each step also carries `at`, the time the server took it. A fixture is the named step of one transcript (a test pins the names and statuses; the transcripts were recorded in a later run than the committed fixtures, so their times, `confirm` tokens and exam draws differ); the setup calls between the named steps are in the transcript and in no fixture, so a replay of a transcript's requests reaches the state the recording had.

`Support/TranscriptReplay.swift` replays a transcript's requests, in order, against any `HTTPTransport` and compares each answer: status, `Retry-After`, and every key and value of the body. It returns no difference when all matched, and otherwise the differences of the first answer that did not. Three kinds of value are not compared as text. A time may be up to 25 ms from the recorded one: the replay first hands the engine's clock the time each request was recorded at, through `Hooks.clock`, and the recorder holds the server's clock at the time it took each request while it answers, and fails a recording in which the server still stamped a time later than that. An id is bound one to one: an id first met in an answer stands for the id the engine answered in its place from then on, and the replay sends the engine's id wherever the recording sent the recorded one (paths, queries, bodies, and the ids handed to `Hooks.write`); an id first met in a request is the client's own and is sent as recorded. A delete `confirm` token is bound the same way, since the server hashes it from the real ids a recording rewrites. A `write` step is handed to `Hooks.write`; a transcript with a write cannot be replayed without one. A request the engine does not serve by design is skipped through `Hooks.serves`: not sent, but its time still reaches the clock in order. An answer whose `questions` the server lists in a random order (the Review runner's) is compared as the same questions in any order, each without its `position`, when `Hooks.shuffles` names its request. `TranscriptReplayTests` replays every transcript against a transport that answers with the transcript itself, and against one that answers with ids of its own, with no difference, and shows that each kind of wrong answer, a broken id binding and a time from another step are what the replay finds.

The server picks an exam's questions at random, so the draw in a recorded exam answer is the recording's; an engine proven by these transcripts takes its shuffle from the caller (`LocalBank`'s `random`).

When the server's API changes, re-record from a checkout of the commit to pin. The script reads that checkout and does not fetch:

```sh
test/record-contract.sh /path/to/qbank-server
```

Then run the package tests.

`Fixtures/bank-archive/server-bank.json` is one bank archive the real server wrote (`GET /api/me/bank`) for a synthetic store account whose bank has a row in every table, an older version of a set, and deleted rows. `test/record-bank-archive.sh /path/to/qbank-server` records it the same way, in-process over an in-memory database with invented data; it needs a checkout that has the route.

A topic is a course row of kind `topic` with no semester and an empty code. `semesters.json` stays the catalog from before this account had topics, with `topics` present and empty, which is how the server sends that list.
